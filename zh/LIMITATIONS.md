## 0. 引用数字之前先看这里

围绕这个移植（以及它所源自的 Vita 移植）流传着不少数字，它们**不能互换**。
两个目标的预算是不同的：

| | Vita 移植（上游） | 本移植（Android arm64） |
|---|---|---|
| 内存模型 | 固定、紧张 | 动态、低 4GB 地址空间 |
| guest 堆上限 | 81 MiB 这一档 | **2640 MB**（2026-11-10 起） |
| 帧预算 | 高度受限 | 60Hz 下约 16.7 ms |

"81 MiB 堆""27 分钟后 OOM""密集房间 33-34 fps"都是 **Vita 的数字**，不描述
这个构建。如果有人拿这些数字质询，先查它是哪个目标的——真实上限在
`host_crt.c` 只有一个地方：

```
grep -n 'define HEAP_END' source/host_crt.c
```

本文件其余数字是这么来的，你可以自己复算一遍，不必相信：

```bash
G=/storage/emulated/0/Android/media/com.isaacport.launcher/files/game

# 帧率采样（[perf] 每 60 帧打一行）
grep -oE '平均 [0-9.]+ ms \([0-9.]+ fps\)' $G/inproc.log | sed 's/.*(\(.*\) fps)/\1/' \
  | sort -n | awk '{a[NR]=$1} END{printf "n=%d 最低=%.1f P10=%.1f 中位=%.1f 最高=%.1f\n",
    NR,a[1],a[int(NR*0.1)+1],a[int(NR/2)+1],a[NR]}'

# 有没有触发过未翻译指令
grep -ciE 'guest_fault|untranslated|untranslated:' $G/*.log

# 内存耗尽
grep -h '堆耗尽\|heap exhausted' $G/*.log
```

## 1. 未翻译指令可能让"能启动"的一局中途崩掉

**状态：未验证的风险。本项目日志里从未出现过。**

翻译器对没实现的指令会生成 **loud stub**（`runtime_patched/guest.h` 里的
`guest_fault()`）。loud stub 是刻意的——见 `PITFALLS.md` 5.11：空 stub 返回 0，
会在毫不相关的地方崩掉；loud stub 直接把指令名写进日志。

**为什么"能启动"证明不了什么。** 启动只走通一条路：CRT 初始化、镜像加载、
GL 上下文、几个菜单。而道具组合、特殊房间、角色和结局会碰到 15,071 个已翻译
函数里大得多的范围。在普通房间里稳定跑一小时，对结局过场**没有任何说明力**。

**指令空间已知是不完整的——确切差 20 个指令。** 这不是开放问题。
`BUILD_SPEC_FOR_AGENTS.md` 第 7 节列了它们：`pabsd`、`pcmpeqd`、`pshufb`、
`vpcmpeqb`、`pmaddubsw`、`movq`、`pxor`、`movd`、`stmxcsr` 和 **`popfd`**，
全是 MMX/SSE。它们在引用路径上（部分被引用 1-3 次），但正常游玩不到。

所以真正的问题不是"缺不缺东西"——缺 20 个——而是"某条具体路径是否会执行其中
之一"。结局、特定道具组合或某个 Mod 会；普通房间不会。

**证据实际说了什么：** 测试设备上保留的全部日志里，`guest_fault` /
`untranslated` **一次都没有触发**。这与"被引用但未到达"一致，不能证明每条
路径都是干净的。

**怎么自己查**——不需要改任何代码，只需要一次打到底的通关：

```bash
G=/storage/emulated/0/Android/media/com.isaacport.launcher/files/game
grep -nE 'guest_fault|untranslated' $G/inproc.log $G/native.log
```

零行 = 整局没跑出已翻译集合。有任何输出，那就是**带地址的完整 bug 报告**，
不是悬案。

**如果触发了：** 正确做法是在生成器里补这条指令分析并重新生成 `gen/`，
不是在宿主层打补丁。在补完之前，新内容里的崩溃应该按"可能未翻译"对待，
而不是直接当成"内存 bug"。

## 2. guest 堆：从 1664 MB 提到 2640 MB，但没有重新验证

**状态：成因已实测，扩容是算术推导，长时间运行未验证。**

这条有真实的设备证据。`std::bad_alloc` 让游戏崩过两次：

```
[heap] ✗ 低 4GB 堆耗尽：bump 已用 1664.0 MB / 上限 1664.0 MB，在外 1254.8 MB（峰值 1259.0 MB），本次请求 24 字节
[cxx]   type[0] = ".?AVbad_alloc@std@@"
[SEGV] sig=6
```

根因是**地址空间**，不是泄漏，而且和空贴图是**同一个原因**：

```
[heap]    bump 已用 1664.0 MB / 上限 1664.0 MB
[texstat] 940 张纹理，其中全零 320 张
```

`malloc` 返回 NULL 时，PNG 解码器放弃写入，贴图保持全零，游戏最终抛
`bad_alloc`。PC 有 4-8 GB，永远走不到这条路径。

**已做的修复（2026-11-10）**——`host_crt.c`：

| | 改前 | 改后 |
|---|---|---|
| `HEAP_END` | `0xB0000000` | `0xF0000000` |
| 跨度 | 1664 MB | 2688 MB（扣掉 48 MB 保留给 token 段） |
| 名义可用 | 1664 MB | 2640 MB |
| 扣掉 ART 的 384 MB 后 | 约 1.28 GB | 约 2.2 GB |

**这不证明什么。** 改完之后没有留下长时运行记录，所以"不再耗尽"是算术，
不是实测。

**分配器把外部碎片转化成了内部浪费。** 它不是纯 bump 指针：自 2026-11-02 起，
每个请求都向上取整到 2 的幂，释放的块回收到 31 条 size-class 空闲链表。这消掉了
最初的故障（纯 bump 分配器一个字节都不归还，半分钟就填满上限），代价是**每个
分配最多浪费 2 倍**：5 MB 的请求拿到 8 MB 块，100 字节的请求拿到 4 KB 块。
所以 2640 MB 上限**不等于** 2640 MB 有效载荷。把 size-class 阶梯改密
（1.25x 或 1.5x 递增，而不是纯 2 的幂）能大幅减少浪费；这件事没有做，而且
改完必须重新验证 MSVC 对齐释放的约定——它要读 `[ptr-4]` 的块头
和 `p+0` 的尺寸，这两个布局事实不能变（`host_crt.c`）。

**还要注意这个耦合：** 940 张纹理里 320 张全零，而全零纹理照样占堆。按
512×512×4 算，大约 **320 MB 被这些什么都不画的图白占着**。所以字体图集缺陷
（见 `README.md`）不只是画面问题——**修掉它会直接缓解那次 `bad_alloc` 的
压力**。这个因果关系在项目停手前没有被动手处理。

**怎么查：**

```bash
grep -hE '堆耗尽|heap exhausted|bad_alloc' $G/*.log
```

## 3. 帧率：有实测，且低于标题数字

**状态：实测。**

`README.md` 写的 58-60 fps 是**较早构建的最好情况**。当前构建 142 个
`[perf]` 采样的实测分布：

```
n=142   最低 2.5   P10 43.6   中位 56.9   最高 60.4
```

老实读这组数字：

- **中位 56.9 fps**——普通房间贴着 60Hz 上限
- **P10 43.6 fps**——每十个采样窗口就有一个慢三分之一
- **最低 2.5 fps**——加载房间。日志里有 `[stall] 单帧 1016.5 ms` 的记录，
  一次房间切换要付掉约一秒的实际时间
- 当前日志里第二严重的停顿发生在帧前的 `free()`，也就是分配器开销，不是渲染

更早的构建中位是 58.4-59.5 fps。**当前构建比那时候慢**，原因是 2026-11-12
排查字体图集时加的诊断探针：

```
当前构建新增的日志 tag：
[alpha] [alphachk] [depthst] [drawstat] [fb] [fbatt] [fbset] [frame]
[keepres] [repair] [settexel] [stubhits] [texppm] [uidraw] [viewport] [zerotex]
```

其中好几个挂在绘制和状态查询路径上。`PITFALLS.md` 6.1 记录过一模一样的
失效模式：每次导入 2 个 `snprintf` × 上亿次 = 启动多 9 秒。**但这些探针从来没有
被单独关掉测过，所以这 3 fps 的差是"归因"，不是"证明"。**

**想要更快的版本：** 重编 `gen/`，把 profiling 探针编掉
（`kage_vita_png_profile_row_begin/end`、`host_settexel_probe`）再实测。别用
静态指令数做决定——`PITFALLS.md` 6.3：指令数少 9.1%，实际时间只差 0.2%。

**调参解决不了的部分：** 翻译后的程序仍要维护 x86 寄存器、标志位和分派路径，
然后穿过图形兼容层。要继续提速往往得把热点改写成原生实现，而每次替换都要
自己做行为一致性验证。

**另一个独立缺陷，不是探针成本：** 在上面那些数字之外，**密集房间**还会掉帧。
`README.md` 把它列为两个已知缺陷之一，`PITFALLS.md` 第 10 节追到 gl4es 的
`ToBuffer()` 被 `vao->locked == 1` 挡住——"修法很清楚"，但从未实施。不要把
它和插桩成本搞混：去掉探针能找回约 3 fps；密集房间掉帧是另一回事，要改那段
代码。

## 4. 版本与 Mod 兼容范围很窄

**状态：实测约束，结构性决定。**

构建锁定 **Repentance 1.7.9b（J835）**。`BUILD_SPEC_FOR_AGENTS.md` 在翻译前
校验可执行文件的尺寸和 SHA-256；不匹配就停，因为 15,071 个函数边界全部是从
那个具体二进制推导出来的。

后果：

- **Repentance+ 或任何更新的补丁**需要重跑分析、重新推导地址。翻译另一个
  构建得到的 `gen/` 对不上。
- **Lua Mod** 依赖函数地址和指令布局，而引擎的 Lua API 面只能经由翻译后的
  代码到达。**测试设备上从未加载过任何 Mod**——所有记录的运行里 `mods/`
  都是空的，日志里没有任何加载序列。所以任何形如"某 Mod 能用"或"某 Mod
  会崩"的说法，在本压缩包里都**没有证据**。整个 Mod 面请当作**未测**。
- **依赖 REPENTOGON 或其他 PC 原生扩展的 Mod** 需要那些扩展也被移植。它们
  不属于本项目。

### 4a. 一次影响所有 Mod 的宿主层限制

在逐个试 Mod 之前，先知道：有三个 Windows 文件 API 的缺陷对**所有** Mod 都
生效，而且读 `host_android.c` 就能确认。它们都不需要装 Mod 复现。

**非 ASCII 名字两个方向都会坏掉。** 两个转换函数是逐字节的，不认 UTF-8：

```c
u8_to_u16:  st16(dst + i*2, (uint16_t)(unsigned char)src[i]);   /* 字节 -> 码点 */
u16_to_u8:  dst[k++] = (w < 0x80) ? (char)w : '?';              /* 非 ASCII -> '?' */
```

实测：UTF-8 名字 `我的模组` 会变成十二个分开的 Latin-1 码点
（`U+00E6 U+0088 U+0091 …`），而不是三个汉字。**任何目录名含非 ASCII 字符的
Mod 都无法被枚举或打开。** 加一遍 UTF-8 解码/编码（来回各约 20 行）可以
一次性修好所有 Mod 的这个问题。

**同时只开 8 个目录句柄。** `#define FIND_MAX 8` 配静态的
`DIR *g_find_dir[8]`。若某个 Mod 在引擎正在枚举时自己递归子目录，就会把这个
用尽并得到假的失败。

**通配符只支持 `*` 和 `*.ext`。** 实测：`*abc*`、`a?c`、`[ab]c` 永远不匹配。
注释说引擎的全部用法（枚举 `mods/`、读 `*.xml`）只用到这两种，对引擎成立；
但 Mod 自己若用更丰富的通配调用 `FindFirstFileW`，会什么都拿不到。

这三个都是**一次性修**，不是逐个 Mod 的工作。

### 4b. 真正需要逐个测的部分

修完上面的宿主限制后，剩下的问题是：某个 Mod 是否碰到了一个没被翻译的游戏函数。

**两个不同的数字，回答的是不同的问题。** `BUILD_SPEC_FOR_AGENTS.md` 两个都记了：

- **15,071 个函数→ 14,920 成功 / 109 未支持 / 42 失败。** 那 151 是**无法完整
  翻译的函数**。
- **20 个未翻译的*指令***，全是 MMX/SSE：`pabsd`、`pcmpeqd`、`pshufb`、
  `vpcmpeqb`、`pmaddubsw`、`movq`、`pxor`、`movd`、`stmxcsr`、**`popfd`**——
  完整列表在 `BUILD_SPEC_FOR_AGENTS.md` 第 7 节。

那 151 个函数失败的原因**就是**它们含这 20 个指令之一，所以真正的计量单位是 20
而不是 151。`BUILD_SPEC` 还写明这些桩**位于被引用的代码路径上**（部分被引用
1-3 次），但正常游玩不会到达——这与本压缩包里所有保留日志中 `guest_fault`
命中为 0 是一致的。

所以一个 Mod 只有在把游戏驱到执行那 20 个指令之一的代码时才有风险。这就是为什么
正常游玩正常的 Mod 可能没事，而某个特定结局或道具交互不是：这是个**路径**问题，
不是**Mod**问题。

这里没有离线捷径。引擎的 Lua API 名字**既不在** `.so` 里**也不在** `gen/` 里
（实测——`strings` 找不到任何 `Isaac.*` 或 `MC_*` 名），所以无法从二进制提取
API 白名单。每个 Mod 跑一次带插桩的会话可以一次回答两个问题，而这是**读日志**
而不是猜：

```bash
grep -c 'guest_fault' $G/inproc.log      # 未翻译指令（会自己报名字）
grep -c 'illegal address' $G/inproc.log  # 地址落在已翻译镜像之外
```

命中会直接打印指令名和地址，所以是定位好的 bug，不是悬案。两行都是 0、
同时 Mod 肉眼可见地工作——只有这个算证据。

## 5. 行为差异：这里无法验证的部分

**状态：未验证。这是诚实的缺口。**

`README.md` 说注释不进产物、两棵树编出字节相同的目标文件。那只证明**注释的
翻译**是干净的，对"翻译后的程序行为与原版一致"**一个字都没说**。这是两个不同
的命题，只有第一个被证明了。

具体可能不同的地方，按严重程度排：

**x87 精度——缺口真实，但修法已验证可行。** FPU 栈目前用 `double` 建模：

```c
double st[8];       /* runtime_patched/guest.h —— 64 位，x87 是 80 位 */
```

真实 x87 寄存器的有效位是 64 位。生成代码里的实测出现次数：

```
fst(    631 处    存/取 ST(0) 地址——MSVC 的 float/double 返回约定
st(     121 处    同上
*fst(c,n) op=      331 处    真正的 x87 算术（fdiv/fmul/fadd/fsub）
```

约 750 处 FPU 栈操作加 331 处算术，摊在 15,071 个函数上。

**修法很小，而且是验证过的、不是推测的。** arm64 Android 上的
`long double` 是 **binary128——16 字节、113 位有效位**，**超过** x87 的 64 位。
实测而非推断：

```
sizeof(long double) = 16
1/3 存为 long double = 0.33333333333333333333   （20 位）
同一个值存为 double  = 0.33333333333333331483   （17 位）
```

331 处算术全部写成 `*fst(c,n) op= (double)ldf(...)`，操作数上已经有显式
`(double)`。因为 `*fst(c,n)` 变成 `long double*` 后操作数会隐式加宽，
**`gen/` 一个字都不用改**——只需把 `st[8]` 和 `guest.h` 里四个 helper
（`fpush`、`fpop`、`fcmp_set`、`fst`）改类型，然后重编。这一点用
单独编译生成代码原样写法验证过。

**代价，实测：** `long double` 算术比 `double` 慢 **29 倍**（本机 19 ns/op
对 1 ns/op）。但只有 331 处做算术，而 FPU 栈访问是存取/拷贝不是运算。
换算到 16.7 ms 的帧预算：

```
每帧 1000 次 x87 运算   -> +0.02 ms  （ 0.1%）
每帧 10000 次 x87 运算  -> +0.18 ms  （ 1.1%）
```

所以只要 FPU 算术不在逐像素或逐粒子的路径上，这个代价就能接受——
调用统计暗示它不在，但**没有在真机上 profile 过**。不要盲改：先测，再定。

**为什么当前的 `double` 仍是风险：** 精度误差在**累积**里放大，不在**传递**里。
750 处里大多数只是传返回值，64 位和 80 位的差在转换那一刻就固定，不会滚雪球。
危险的是碰撞或物理循环在 x87 里反复累加，而这种模式在统计里看不到。
**这里没有任何东西证明当前构建是错的**——只证明它不是精确的，而把它变精确
是五行改动加一次重编。

**线程与时序。** guest 跑在单线程串行分派器上，真实的 Windows 工作线程没有
在跑。`PITFALLS.md` 6.2 记过一例（无条件的 `usleep` 把帧率钉在 30fps）。
任何依赖真实并行度的东西——原版能容忍的竞态、原版依赖的顺序——都可能表现
不同或根本不会发生。

**文件与图形状态。** FUSE 上 `access()` 会说谎，进程内 `dup2` 被禁止，符号
链接进不了 APK（`PITFALLS.md` 2.x）。这些都有绕法，但绕法的行为一致性只到
"被测过的程度"为止。

**怎么验证——以及代价。** 唯一可靠的方法是**同种子对照**：同一种子在 PC 和
设备上跑，逐帧比对状态。这需要给 PC 端加插桩输出状态哈希，而**本项目不含这个
东西**。它没有做，也无法仅凭这个压缩包做到。想拿到行为保证的接手者，得先把
这套对照装置搭起来。

达不到这个标准的一切说法——"感觉一样""没崩"——都不构成行为等价的证据。
报 bug 时请照直这么说。

## 8. 哪些事没做，做了要多久

这一节存在的原因是项目停了。上面那些条目不是"有人在做"——**没有人在做。**
下面是停手那一刻已经摸清的范围：改动落在哪、实测要多久、为什么没做。

原作者不会再验证其中任何一条。这里所有数字都只是**一台设备上的起点估算**，
不是承诺。

### 8.0 为什么放弃

**不是因为没兴趣，也不是因为剩下的活看起来难。停手是因为「改—编—测」这个
循环在手上的硬件上太吃真实时间。**

整个移植是在**一台跑 Termux 的安卓手机上**做的。没有 PC、没有工作站、没有
CI。这一个事实解释了本文档里大部分决定，包括几个否则看起来像偷懒的：

**每次构建都是全量构建。** 没有可行的增量链接办法，所以改 `guest.h` 一行就
要重编全部 192 个翻译单元——208 MB 生成的 C，最大单文件 4.9 MB。本机实测：
**最大单个单元 7.9 秒**；8 路并行下 16 个中等单元用 **16.4 秒**、4 个最大单元用
**8.7 秒**。按体积外推约 **3.5 分钟**，`BUILD_SPEC_FOR_AGENTS.md` 第 7 节记录的是
**6-8 分钟**，而内存压力下的全冷启动实测接近 **15-20 分钟**。这个跨度是真实的：
这台手机有 15 GB 内存和 8 核，同时编 8 个单元是**内存瓶颈**而不是 CPU 瓶颈。
**规划时按 10-20 分钟算**——那才是一次真实迭代的体感，本文档其余部分引用的也是
这个数字。

**每次测试都要人动手。** APK 必须点安装——`pm install` 被 SELinux 拒绝
（§8e）——日志还要从设备里读回来。所以循环不是 `改 → 编 → 观察`，而是：

```
改 → 全量重编（10-20 分钟） → 重打包 APK → 手动点安装
   → 玩到 bug 出现（几分钟到几十分钟） → 取日志 → 读 → 再来
```

**一次迭代 20-30 分钟，而且大部分是等待**，而难缠的缺陷——空字体图集、掉帧
——需要很多次迭代，因为每次只能排除一个假设。这就是两个缺陷以未修状态发布、
以及 51 fps 被接受而不去追查的全部原因：工作本身并不神秘，而是每个实验在手机上
要花半小时。

**这不能开脱什么。** 本文档里的测量仍然是测量，缺陷仍然是缺陷。硬件限制解释了
工期，它不会让这个构建变得已验证。§8e 里关于"运行期行为未被观察"的一切仍然
成立。

**如果你有 PC，这个项目完全是另一回事。** 同样的全量重编在桌面上只要几分钟，
而且可以用 ADB 驱动设备而不是手点。仅这一个改变，就能让 8b-8d 那几项工作从
"昂贵"变成"日常"。

**"一台桌面电脑"具体指什么。** 在本树上实测：8 个单元并行编译时，所有 clang
进程的 RSS 峰值合计 **1.48 GB**。所以任何 x86-64 机器配 **8 GB 内存**都很宽裕，
16 GB 可以同时跑 16 个编译。**不需要显卡**——构建期不渲染任何东西，gl4es 只是被
链接进去、不运行。2015 年的笔记本就够。构建也不碰设备，手机只在最后测试时要用。

### 8a. 构建步骤的实测耗时

在开发机（8 核、Android/Termux、clang 21）上计时。列出来是因为它说明瓶颈
**不在**工具链：

```
编译单个 host_*.c           0.24 秒
链接 70.5 MB 的 .so         0.43 秒   （227 个目标文件，复用已编好的 .o）
重打包 + zipalign + 签名    1.78 秒
```

真正的成本在改代码和验证，不在构建。改一个宿主文件只要几秒；改 `guest.h`
要**重编全部 192 个 `gen/` 单元**（约 15-20 分钟）。

### 8b. 工作项一：三个模组/文件 API 缺陷（最便宜、风险最低）

全部落在 `source/host_android.c`。行号取自本压缩包的版本：

| 什么 | 位置 | 怎么修 |
|---|---|---|
| 非 ASCII 文件名/模组名被破坏 | `u16_to_u8()` 848 行、`u8_to_u16()` 860 行 | 真正的 UTF-8 ⇄ UTF-16 转换（来回各约 20 行） |
| 同时只能开 8 个目录句柄 | `#define FIND_MAX 8` 842 行 | 提到 32，或把句柄表改成动态分配 |
| 通配符只有 `*` / `*.ext` | `name_matches()` 890 行 | 补 `?` 和通用 `*` 匹配 |

预计：**20-30 分钟**编辑，然后编译（0.24 秒）、链接（0.43 秒）、上机确认。

**为什么这项性价比最高：** 它不需要重编 `gen/`，所以**不可能**改变任何翻译
函数的行为。影响面就是一个文件。

### 8c. 工作项二：x87 改用 `long double`

改 `runtime_patched/guest.h` 里的 `st[8]` 加四个 helper（`fpush`、`fpop`、
`fcmp_set`、`fst`）。`gen/` 不用改——第 5 节已验证。

预计：**5 分钟**编辑，加**重编全部 192 个 `gen/` 单元**（约 15-20 分钟），
再上机实测。

**为什么没做：** 它会重建整个 `.so`，等于 15,071 个翻译函数同时变化。
`long double` 算术实测慢 29 倍，而没有真机 profile 能说明 FPU 运算是否在
热路径上。改完不测帧率就动手，等于拿本项目唯一可靠的数字（中位 56.9 fps）
去赌。

### 8d. 工作项三：去掉诊断探针

第 3 节列的那 16 个日志 tag 是 2026-11-12 排查字体图集时加的。去掉它们需要
把 profiling 钩子编掉后重编 `gen/`（`kage_vita_png_profile_row_begin/end`、
`host_settexel_probe`）。

预计：**20 分钟**加上同样的全量重编。

**为什么没做：** 那 3 fps 的差是"归因"，不是"证明"。去掉探针再测就能定论；
没有人做这个测量。

### 8e. 为什么这些全都没被验证

两个独立原因，而且都不是"再努力一点"能解决的：

1. **原作者停手了**——原因见 §8.0（是在手机端硬件上的迭代成本问题，不是没兴趣）。
   以当前状态发布是刻意的。
2. **做最后一轮工作的 agent 无法在设备上测试。** 它在本地构建了一个 APK
   （一次性的临时产物，从未发布——见 `DISTRIBUTION.md`），但装不上：
   从 Termux shell 里 `pm install` 被 SELinux 拒绝：

   ```
   avc: could not determine enforcing mode: Permission denied
   Unknown class fileSystem server has no access to read file context
     u:object_r:fuse:s0 (from path /storage/emulated/0/Download/...apk)
   Error: Unable to open file
   ```

   `/data/local/tmp` 在这里也写不进去。所以工作循环是
   **改 → 构建 → 把文件交出去**，从来不是 **改 → 构建 → 观察**。代码靠编译
   和目标码比对验证；**运行期行为完全没有验证。**

   这一点值得说透，因为它限定了这个压缩包能声称什么。**写这份文件的 AI 从来
   没跑过这个游戏。** 文件里所有**设备上**的实测数据都来自**原作者**在手机上
   产生的日志。AI 自己测的只有**构建**成本（8a 里的编译 0.24 秒、链接 0.43 秒、
   重打包 1.78 秒），验证的只有代码能编过、目标文件一致。**本文作者没有观察到
   任何运行期行为**——没有帧率、没有崩溃、没有模组能否加载。

### 8f. 如果你要接手

一个可行的顺序，按"每一步都能独立验证"来排。**下面每一步都要先有一个设备版
构建**——本压缩包既不含 `.so` 也不含 APK，所以先自己把两者构建出来（S7/S8）；
安装细节见 8g。

1. **模组/文件 API（8b）。** 一个文件，不重编 `gen/`。验证方式是装一个目录名
   含非 ASCII 的模组——修之前它根本枚举不出来，所以结果没有歧义。
2. **帧率（8d）。** 去掉探针重编、实测、和这里的 142 个采样对比。这是找回
   已知性能最便宜的办法。
3. **x87（8c）。** 只在第 2 步之后做，而且必须在改前改后各测一次帧率。如果
   每帧多出超过约 1 ms，就回退。
4. **一致性对照装置。** 拿到行为保证的唯一路径（第 5 节）。没有捷径。

不要从第 4 步开始。它最大，而且卡在本压缩包不包含的 PC 侧插桩上。

### 8g. 上机验证到底需要做什么

**这个压缩包里没有任何能直接跑的东西。** 里面没有 APK 也没有 `.so`，这是刻意的
（见 `DISTRIBUTION.md`）。所以上机验证之前，你必须自己构建：
`BUILD_SPEC_FOR_AGENTS.md` 的 S7 链接 `.so`，S8 用 `apk/build_apk.sh` 打成 APK。
链条是：**本地构建 → 安装 → 迭代**。

**安装有一个不明显的限制：** APK 必须**手动点安装**（文件管理器或系统安装器），
不能从终端装。这一点是实测的——`pm install` 被 SELinux 拒绝，`/data/local/tmp`
从 Termux 也写不进去。这正是 8e 把"装不了"列为真实障碍而不是偷懒的原因。

**装上去之后**，后续宿主层的改动完全不用重装。外置 `.so` 通道接手：

```
/storage/emulated/0/Android/media/com.isaacport.launcher/files/game/libisaac.so
```

这个目录从 Termux 可写（已实测），而 `MainActivity` 里的 `resolveSoPath` 会对
文件做指纹（长度 + mtime + 首尾哈希），变化后自动拷进私有目录。所以第一次
安装之后，宿主层改动的循环是：**替换那个文件 → 重开 App → 读日志。不用重打
APK，不用重装。**

日志就在旁边：`app.log`、`inproc.log`、`native.log`。

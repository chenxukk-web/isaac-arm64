# 启动时间与 `ARCH000` 归档

2026-11-27 实测，设备与本归档其他所有数据相同（Adreno 830 / Android 17）。
下面每个数字都来自一次运行，不是估算；凡是推断的地方都注明了。

**摘要：** 启动约 17.5 秒在加载资源，其中 97% 是 `inflate()` 在跑翻译过的
x86。把归档重新打包、让游戏完全不需要 inflate，可降到 8 秒——已实测。
这个改动被一个既有的内存 bug 挡住，而那个 bug 是被文件大小变化触发的。
**启动没有任何缓存**：每次启动都重新解压同样的 1.2 GB。

---

## 1. 17.5 秒花在哪

正常启动的 `[boot]` 标记：

```
T+      0.0 ms  main 进入
T+     89.0 ms  PE 镜像加载完成        （141 MB 的 .so，89 ms）
T+    109.6 ms  GL/宿主初始化完成
T+    325.7 ms  第一帧渲染完成
T+ 17,804.4 ms  第一次 XInput 轮询     ← 游戏加载完了
```

同一标记在其他几次运行里是 16.4 秒和 21.2 秒，所以正常范围是 17-21 秒。
第一帧到第一次轮询之间的 17.5 秒就是资源加载。

已用测量排除的候选：

| 候选 | 证据 | 结论 |
|---|---|---|
| 打开文件 | 私有目录（ext4）上 `fopen` 是 **5.64 µs**；22,522 次归档打开 ≈ 0.13 秒 | 不是瓶颈 |
| 读取数据 | 1.2 GB 按 1.1 GB/s 读 ≈ 1.1 秒 | 不是瓶颈 |
| PE 镜像加载 | 141 MB 用 89 ms | 不是瓶颈 |
| GL/宿主初始化 | 11 ms | 不是瓶颈 |
| 导入分发 | 加了指针缓存后毫无变化（仍是 16-22 秒） | 不是瓶颈 |

剩下的是 `inflate()` 里的 CPU 时间，而这里的 `inflate()` 是**翻译过的 x86**，
不是原生库：zlib 静态链接在 `isaac-ng.exe` 里，所以和其他代码一起被提升成了
C。导入表里没有任何 `inflate`/`uncompress` 项（已验证：`gen/guest_table.c`
里零匹配）。

同样数据用原生 zlib 跑，用本归档里的 `bench_arch.c` 测得：

| 归档 | 直存块 | deflate 块 | 原生耗时 |
|---|---|---|---|
| `afterbirth.a` | 129,236 | 39,022 | 0.56 秒 |
| `afterbirthp.a` | 113,638 | 56,523 | 0.77 秒 |
| `repentance.a` | 350,691 | 59,999 | 0.96 秒 |
| 其余 11 个小归档 | — | — | 0.16 秒 |
| **合计** | **671,439** | **187,035** | **约 2.5 秒** |

同样的字节、同一台机器：**原生 2.5 秒 vs 翻译代码 17.5 秒——7 倍差距。**
这个倍数就是翻译层的代价，也是启动时间的全部故事。

### 1.1 没有缓存

一次启动读 1.2 GB、inflate 出 166 MB，而**这些都不会被保存**。`packed/` 下
没有任何文件是缓存，宿主层不在运行之间保留归档状态，`host_crt_file.c` 还
显式关掉了它的持久 `FILE*` 缓存。**每次启动都从头重做。**

## 2. `ARCH000` 格式

格式取自 `caos-obliquo/tboi-recomp` 的 `docs/arch000-format.md` 和
`src/data/codec.cpp`（GPL-3.0，作为参考资料阅读，未拷贝代码），再用本安装里的
零售归档逐项验证。

```
0x00  8 字节    "ARCH000" + 一个 mode 字节
0x08  u32       条目索引的偏移
0x0C  u16       条目数
0x0E  ...       载荷
索引  count * 20 字节，在文件末尾
```

`index_offset + count * 20 == file_size` 在本机每个归档上都成立。

每个索引条目 20 字节：

| 偏移 | 字段 |
|---|---|
| +0x00 | `hash_lo` —— 资源路径（小写化）的 32 位 djb2-add(5381) |
| +0x04 | `seed` —— 每条目的加密种子（**不是** 64 位哈希的高半部分） |
| +0x08 | `offset` —— 跨条目严格递增 |
| +0x0C | `size` —— **解压后**长度 |
| +0x10 | `crc` |

三种 codec，由 mode 字节选择：

| mode | 归档 | 行为 |
|---|---|---|
| `0x00` | graphics、music、sfx、videos | Bogocrypt1：XOR + 条件交换 + 密钥调度。对称。 |
| `0x01` | config、fonts、rooms、animations | LZW：字典跨一个条目的 4 字节前缀块保留；宽度先增后读。 |
| `0x02` | afterbirth*、repentance*、所有语言包 | 4 字节长度前缀 + 裸 DEFLATE（`wbits=-15`）；长度恰为 `0x400` 的块是**加密的**，不是直存——见 §3.0 的更正。 |

### 2.1 名字解析

用官方资源路径清单可以反查 `hash_lo`，清单在本归档里：

```
work/recourse/(pc)tboi,rep/tools/ResourceExtractor/filelist.txt   （18,328 条）
```

对 22,522 个已安装条目的实测覆盖率：

```
解析成功 20,676 / 22,522 = 91.8%
```

比上游报告的 81.46% 高，因为本安装的清单更新。未解析部分集中在
`afterbirth_jp.a`、`afterbirth_kr.a`、`rooms.a`（3/13）和 `animations.a`（0/1）。

### 2.2 归档里究竟装了什么

`fonts.a` 装的是十个 `.fnt` 位图字体描述，不是 PNG：

```
resources/font/pftempestasevencondensed.fnt
resources/font/teammeatfont10.fnt
resources/font/teammeatfont12.fnt
resources/font/teammeatfont16.fnt
resources/font/teammeatfont16bold.fnt
resources/font/teammeatfont20bold.fnt
resources/font/upheaval.fnt
resources/font/droid.fnt
resources/font/terminus.fnt
resources/font/terminus8.fnt
```

10 个全部能解析、10 个全部能解压。**字体 PNG 不在 `fonts.a` 里**——它们在
`graphics.a`、`afterbirth.a` 和 `afterbirthp.a` 中（`resources/font/teammeatfont16_0.png`
在 `graphics.a` 和 `afterbirthp.a` 里都有）。

**与缺字体缺陷有关的一条线索：** 从 `fonts.a` 解出来的 `.fnt` 是**英文原版**
（`Team Meat font`），而 `resources/font/` 下的散文件是中文汉化版
（`Team Meat Font X HappyZCool`）。两者都引用 `TeamMeatFont16_0.png`（大小写
混合），而磁盘上的文件是全小写。**这条线索值得继续查，但尚未验证。**

## 3. 重新打包让游戏不再 inflate —— 已实测，被挡住

### 3.0 更正：`0x400` 块是加密的，不是直存

**本节此前断言 `0x400` 块是原样直存。这是错的，基于它的重打包会破坏数据。**
保留在这里，因为这是个有教育意义的错误，而且读过早期版本的人需要知道。

chunk 循环确实对长度 `0x400` 有一条快速路径（下面的反汇编就是它），但那条
路径**做的是解密**。它调用两个函数：

```
0059c412  call sub_005ec14c
0059c422  call sub_005b06f0
```

`sub_005b06f0` 是一个 PRNG 密钥驱动的 XOR 循环——42 条指令，函数体每个字推进
一次状态并查一次密钥表：

```
005b0715  mov ecx, dword ptr [eax]
005b0717  mov eax, dword ptr [ecx]
005b0719  mov edx, dword ptr [ecx + eax*4 + 4]
```

上游鸿蒙移植把同一地址认定为 `isaac_archive_xor_try`，即它的解密入口，所以这不
是只凭形状推断的。

**决定性实验。** 把 `repentance.a` 的条目按"是否含 `0x400` 块"分成两组，逐条
对归档自带的 fold 校验和：

```
纯 DEFLATE 的条目        1531 / 1531 通过
含 0x400 块的条目           0 /   29 通过
```

同一个解码器、同一条代码路径——唯一的差别就是那个 `0x400` 块。如果这些块是明文，
第二行也应该通过。

**这对 §3.1 和 §3.2 意味着什么。** 重打包把 DEFLATE 块转换成装着其明文的
`0x400` 块。既然游戏会解密它读到的每个 `0x400` 块，那些明文就会被再解密一次，
出来就是噪声。§3.1 的逐字节比对没能发现这一点：两边都用同一个解码器读，而这个
解码器把 `0x400` 当明文，所以两边互相一致，同时一起和游戏不一致。

§3.2 实测的 8 秒启动仍然成立——游戏真的不再调 `inflate` 了——但**这个重打包在
数据上不正确，不能就这样发布。** 解密那些块是未完成的工作；PRNG 的播种方式这里
没有恢复出来。

---

### 3.0a 导致错误结论的那段反汇编

游戏有一个 chunk 循环，对长度恰为 `0x400` 的块有一条快速路径。在翻译代码里可以
直接看到（`gen/guest_0172.c`，含 RVA `0x59c341` 的那个函数）：

```
0059c39e  mov al, byte ptr [edx + 0x10]   ; 是否已解码的标志
0059c3b9  cmp esi, 0x400                  ; 这个块是不是恰好 1024 字节
0059c3bf  jne 0x59c3c5                    ; 不是 -> 清标志
0059c3c1  mov al, 1                       ; 是   -> 置标志
0059c3cc  jne 0x59c40c                    ; 标志已置 -> 走快速路径
...
0059c412  call sub_005ec14c               ; 快速路径：直接搬运
```

而 97.1% 的 deflate 块解出来**恰好是 1024 字节**：

```
解压输出长度        次数        占比
1024 字节         149,518      97.1%
其他                4,461       2.9%
```

所以一个 deflate 块可以离线替换成装着同样 1024 字节的直存块。游戏随后做
`memcpy` 而不是 `inflate`。

### 3.1 字节等价验证

本归档里的 `repack_stored.py` 把所有输出恰为 1024 字节的 deflate 块转成直存块，
其余原样保留，然后用新偏移重建索引。验证方法是：用同一个读取器解开原始归档和
重打包归档，逐条目比对：

```
repentance.a      4,180 条目    一致 4,180    差异 0
afterbirth.a      2,647 条目    一致 2,647    差异 0
afterbirthp.a     5,512 条目    一致 5,512    差异 0
repentance_zh.a     943 条目    一致   943    差异 0
```

**这个检查证明不了它本来想证明的事。** 两边都是用同一个解码器读的，而那个解码器
把 `0x400` 块当明文（就是 §3.0 更正的那个错误）。所以这个比对只证明了两个归档
*在那个解码器看来*一样——而这是必然的：重打包把字节从一种块搬到另一种块，一个
不区分这两类块的读取器看不出这个搬运。它没有证明游戏读到的数据相同。

真正能定论的做法：先正确解密 `0x400` 块，再比对。那需要 PRNG 的播种方式，而它
没有被恢复出来。在那之前，这个重打包只是一个计时实验，不是可以发布的改动。

### 3.2 真机结果

| | 启动标记 | 崩溃 |
|---|---|---|
| 原始归档 | **T+ 17,804 ms** | 无 |
| 14 个归档重打包 | **T+ 8,000 ms** | **启动期 SIGSEGV** |

**省下 9.8 秒，与「原生 2.5 秒 vs 翻译 17.5 秒」的差距吻合。** 方案成立。

### 3.3 它暴露的崩溃

```
体积       14 个重打包归档：719.1 MB -> 831.1 MB（+112 MB，+16%）
崩溃       [SEGV] sig=11 fault_addr=0x87e7fff0
位置       DInput 初始化期间，也就是归档读完之后很久
堆日志     "[heap] 跳过已占用区 0x87e80000..0x9fe80000"
```

出错地址是 `0x87e80000 - 16`：**比分配器自己报告的已占用区边界低十六字节。**
这是分配块末尾的越界写，不是归档损坏——那时游戏早已读完资源，正在初始化输入
设备。

本次会话里同样的失效模式出现了三次，每次都发生在一个改变内存布局的改动之后：

| 改动 | 结果 |
|---|---|
| 原始代码 + 原始归档 | 600 帧不崩 |
| `host_gl4es.c` 里加诊断探针 | 第 77 帧 abort |
| 重打包全部归档 | 启动期 SIGSEGV |
| 只重打包 `repentance_zh.a`（+3.5 MB） | 不崩，786 帧 |

`[heap] 释放了仍在资源表里的对象` 在**每次运行里都出现 10 次**，包括那些存活
下来的。那个 double-free 是既有问题、与本工作无关；它最可能是上面那个越界写的
来源。

### 3.4 小规模重打包没有结论

只重打包 `repentance_zh.a`（17.1 MB -> 20.5 MB，+3.5 MB）**没有崩**，但也回答
不了启动问题：那个归档只占全部的 1.7%，即使完全免解压也会淹没在噪声里。那次
测得的启动是 T+ 37,218 ms，比基线还**差**，因为替换文件会迫使 Java 层把 2.2 GB
资源全部重拷到私有目录，顺带冲掉页缓存。

**实验设计是错的**，记在这里以免重犯：一次全量重拷约 30 秒，所以单归档实验测
不出启动变化。只有全量重打包才产生足够大的信号——而那个配置恰好会崩。

## 4. 与官方移动版的对比

官方 Android 和 iOS 版**根本不用这个格式**，这就是它们启动快、而它们的做法不能
直接照搬的原因。

在发行二进制上实测：

| | PC（本项目翻译的对象） | iOS `isaac.arm64` | Android APK |
|---|---|---|---|
| `ARCH000` 支持 | 有，22 个归档 | **0 处** | **0 个 `.a` 文件** |
| 资源形式 | 打包归档 | 经 `CFBundle` 读散文件 | `assets/` 下 586 个散 PNG |
| Lua 引擎 | 有 | **0 个 `lua_*` 符号** | — |

iOS 版是另一个引擎：没有归档层，没有 Lua。它 3 秒启动不是这个版本跑得更快，而是
**它做的事更少**——它直接读那些从未被压进容器的散文件。

**本项目翻译的是 PC 可执行文件，所以它继承了 PC 的数据层**，包括归档。
在不丢弃翻译的前提下，预解压是唯一能取得同等效果的办法。

## 5. 已证实的与未完成的

**已由测量证实：**

- 启动基线在 16.4-21.2 秒之间；17.5 秒花在 `inflate()` 里。
- 同样的工作原生 zlib 只要 2.5 秒；翻译层带来 7 倍代价。
- 97.1% 的 deflate 块解出来恰好 1024 字节。
- `0x400` 块是**解密**的，不是拷贝：纯 DEFLATE 条目 fold 通过 1531/1531，
  含 `0x400` 块的条目通过 0/29。
- fold 校验和是 `rotr32(s,1) + word`，初值 `0xababeb98`，`0x200` 暂存区**只清零
  一次**，所以不满的最后一块保留上一块的尾部字节。这个细节弄错的话是 200 条里
  只过 55 条，而不是 200 条全过。
- 有了这个校验和：mode `0x00` 的解码 **2701/2701** 全部正确（graphics、music、
  sfx、videos），mode `0x01` 是 **46/48**（config 24/24、fonts 10/10、
  rooms 12/13、animations 0/1）。
- 全量重打包把启动降到 8 秒，**并且**在输入初始化阶段崩溃。
- 启动之间没有任何缓存。

**未证实 / 未完成：**

- 崩溃被归因于一个既有的越界写和一个独立的 double-free；没有人定位到那条写指令。
- 重打包从未完整跑完一局而不崩。
- **重打包在数据上不正确。** 它把明文变成 `0x400` 块，而游戏会解密这些块，所以
  结果就是噪声。那些块的 PRNG 播种方式没有恢复出来；在恢复之前，重打包只是一个
  计时结果。见 §3.0。
- 因此 mode `0x02` 的解码是不完整的：只有不含 `0x400` 块的条目能通过校验
  （`repentance.a` 里是 1531/4180）。
- §2.2 里那个 `.fnt` 语言不一致尚未测试。
- 1,846 个条目（8.2%）没有解析出名字；`rooms.a` 和 `animations.a` 解得不完整
  （12/13 和 0/1）。
- 没有做任何尝试去减少 +112 MB 的体积增长。

**谁接手的话：先修那个越界写。** 其他一切都卡在它上面，而重打包一旦落地就是
已验证的 10 秒收益。

# 踩过的坑（完整清单）

> **这份文档是本项目最有价值的部分。**
> 每一项都真实踩过，附有当时的证据（地址、日志、数字）。
> 原作者已停止维护 —— 遇到问题时先在这里找，很可能已经有人替你踩过了。
>
> 按**代价**排序：前面的是花掉几小时到几天的，后面的是几十分钟的。

## 一、构建期：会直接让你白跑的

### 1.1 ★★★ 基址不能直接生成，必须二次平移

**症状**：`PE load failed: cannot allocate fixed guest image`

**为什么**：`gen_all.py --image-base` 只接受 `0x30000000` 和 Vita 的
`0x98000000`。新基址要重算 `COVERAGE_CROSS_ROOT_CONTRACTS_BY_IMAGE_BASE`
里的覆盖率契约哈希，代价很高。而 Android app 进程里 ART 的
`dalvik-main` 堆占着 `0x08900000..0x38900000`，**`0x30000000` 正好在里面**，
所以必须在生成之后文本平移到 `0x3C000000`。

**关键细节**：平移**必须同时处理 `host_*.c` 和 `jni_bridge.c`**。
宿主层也硬编码了镜像地址（资源表探针、xinput 的 xprobe 等）。
只平移 `gen/` 会留下不一致 —— 编译能过，运行时行为诡异。

**验证**：跑起来后 `[boot]` 段必须是 `✓ image loaded base=0x3c000000`。

### 1.2 ★★★ `-DSTATICLIB=ON` 漏了会链接失败

**症状**：链接时 `cannot find -lGL` 或找不到 `libGL.a`

**为什么**：gl4es 的 `src/CMakeLists.txt` 是这么分支的：

```cmake
elseif(STATICLIB)
    add_library(GL STATIC ${GL_SRC})
else()
    add_library(GL SHARED ${GL_SRC})
```

不加 `-DSTATICLIB=ON`，产出的是 `libGL.so` 而不是 `.a`。

### 1.3 ★★ `--version-script` 漏了会污染 ART 符号空间

**症状**：`.so` 从 74 MB 变成 75 MB，`dlopen` 后行为诡异

**为什么**：不加的话会导出 **31,104 个符号**（含 466 万行生成代码里的
所有 `sub_XXXXXXX`）。`dlopen` 进 app 进程后这些名字和 ART / 系统库 /
其它 `.so` 的符号空间混在一起：查找变慢，而且万一撞名会「解析到别人」。

**验证**：
```bash
readelf -sW --dyn-syms libisaac.so | awk '$5=="GLOBAL" && $7!="UND"' | wc -l
# 必须是 8
```

### 1.4 ★★ 删非 static 函数前必须搜所有目录（含预编译 .o）

**事故**：删掉 `heap_seg_count()` —— 本文件内已无引用，但 **runtime 的
`guest.c` 仍调用它**，而 `guest.o` 是预编译的。结果编译通过、链接通过，
真机 `dlopen` 失败，白测一轮。

**现在的防线**：`rebuild_pic.sh` 第 6 步校验所有强未定义符号，构建期就
fail。**不要为了让它通过而放宽这个闸门。**

### 1.5 ★★ 增量编译的判据必须同时看 `.c` 和 `.h`

**症状**：改了 `guest.h`，编译产物里还是旧逻辑 —— 编译能过、运行不对，
而且是静默的。

**原因**：只比 `.c` 的时间戳，头文件改了不触发重编。

### 1.6 ★ `duplicate symbol` —— 同一个函数被翻译两次

**事故**：`gen/` 和 `gen_extra/` 里有同名函数，链接报
`duplicate symbol`。`gen_extra/` 是手工修正版，必须从 `gen/` 里排除。

## 二、ABI 与调用约定：错一位，全盘皆错

### 2.1 ★★★ GL 桥把 275 个入口的浮点参数当整数传

**症状**：`glClearColor(0,0,0,1)` 变成乱值 → 切房间出红色块

**根因**：签名解析 `kind_of()` 拿**含变量名的完整声明**（如 `"GLfloat r"`）
去和类型名（`"GLfloat"`）比较，永不相等，于是 16 种签名全退化成 `'i'`。

**后果**：x86 上所有参数都在栈上，arm64 上前 8 个整数进 x0-x7、
前 8 个浮点进 v0-v7。把 `glVertex3f(1.0f,2.0f,3.0f)` 的 float 位模式当
整数塞进 x0，gl4es 收到的是 `0x3F800000` 而不是 `1.0f`。

**修法**：先剥变量名再匹配类型；数组形参（C 里退化为指针）一律按 `'i'` 传。
**已加构建期闸门**：签名表里没有 `'f'`/`'d'` 就报错退出。

### 2.2 ★★★ JNI 函数指针少声明一个参数 → 真机 SIGSEGV

**事故**：`jstring_to_c` 里写成
```c
typedef const char *(*fn_t)(void *, void *);   /* 只声明两个参数 */
```
但真实签名是三个：
```c
const char* GetStringUTFChars(JNIEnv*, jstring, jboolean *isCopy);
```

AArch64 下第三个参数走 x2。只声明两个时 x2 保留**上一个 call 的残留值**，
而 ART 的实现会 `if (isCopy != NULL) *isCopy = ...` → 往垃圾地址写。

**真机证据**：
```
*** 崩溃 sig=0b code=01 addr=000000000023 stage=41 ***
```
`addr=0x23` 就是那个残留值。

**这条解释了历史上所有"无法解释的段错误"** —— 它一直是 UB，有时候 x2
凑巧是 0 或可写地址就"没崩"，否则当场死。**修复：显式传 NULL。**

### 2.3 ★★ `_beginthreadex` 的参数个数必须从调用点实测

**事故**：`basic_iostream::basic_iostream(streambuf*)` 的调用点压了**两个**
push：
```
0065c9da  push 0        ; 第 2 个参数
0065c9e6  push edi      ; 第 1 个参数 = streambuf
0065c9e7  mov ecx, ebx  ; this = stream
```
所以清理 8 字节而不是 4。少清 4 字节会让调用者的栈失衡，之后每个
`[ebp-x]` 都读到错位的值（实测症状：memcpy 的目标地址变成 `0xfffffffe`，
即把某个 -2 的返回值当成指针）。

**教训：参数字节数必须从反汇编实测，不要照 SDK 头文件抄。**
实测和头文件在 `SteamAPI_RegisterCallback` 上就不一致。

### 2.4 ★★ 32 位 `SYSTEM_INFO` 是 36 字节，不是 64

**事故**：`memset` 写了 64 字节，而 guest 侧只开了 `sub esp,0x38`
（56 字节）的局部缓冲区，多写的 8 字节正好落在 `[ebp]` 保存槽和返回地址上。

**这是 2026-11-02 栈帧失衡的根因**：`sub_005e77d0` 的 `pop ebp` 取到 0，
之后所有 `[ebp-…]` 访问崩塌。

### 2.5 ★★ `_set_app_type` 是 cdecl，不能按 stdcall 清参数

MSVC 把三次调用合并成一次 `add esp,0xc`，所以绝不能按 stdcall 逐次清。

## 三、内存分配器：最危险的一类 bug

### 3.1 ★★★ 分配器"返回不足的块"比返回 NULL 危险一百倍

**事故**：请求 8.5 MB，拿到了 8 MB。不报错、不留痕迹，把越界写伪装成
「某个对象莫名其妙变了内容」。为此花了**七轮**排查。

**现在的防线**：
- size-class 分配器必须有"不够就失败"的出口
- 用 `bsz < need` 双保险
- `low_malloc` 超过最大 size class 时返回 NULL，**不返回不足的块**

### 3.2 ★★★ 失败分支不许推进指针

**事故**：`low_alloc` 的 mmap 失败分支不推进 `g_bump`（本意是「避免留洞」），
于是此后**每一次** `low_alloc` 都同样失败、同样返回 0。上层拿到 NULL，
Lua 的 `luaL_requiref` 直接崩。

留一个"已计入却没映射"的洞，崩溃现场会指向一个看起来完全合法的地址。

**正确做法**：`mmap` 失败时**挪 64KB 重试**，而不是原地卡死。

### 3.3 ★★★ `calloc` 必须显式清零

**事故**：代码里曾写着「mmap 已是 0」—— 那只在 bump 分配器下成立。
改成 size-class 复用之后，同一块会被反复分配，里面是上一个使用者留下的数据。

实测：一个 `calloc(1,28)` 的哈希表对象拿到了上一个 `std::string` 的缓冲区，
`[+0]` 是 `0x746e6f66`（`"font"`），被当成桶数送进 rehash → 素数表越界
→ **805 MB 的 memset**。

### 3.4 ★★ 低 4GB 约束：guest 指针是 uint32_t

任何交给 guest 的**指针**必须是低 4GB 地址。只有 `ALCdevice*` /
`ALCcontext*` 是"真指针"形状（真 OpenAL 返回的就是堆指针）。
`HDC` / `HGLRC` 在 Win32 里本来就是内核小整数句柄，用带 tag 的小整数
（`0x00DCxxxx` / `0x00ACxxxx`）既不会和镜像地址混，也绝不会被当成
可解引用指针去踩内存。

### 3.5 ★★ `realloc` 的用户可用大小 = 块大小 - 块头

不能拿块大小直接当数据长度，否则会多拷 16 字节。

## 四、Android 平台特有

### 4.1 ★★★ `access()` 在 FUSE 上撒谎

`/storage/emulated` 走 FUSE，`access(F_OK)` 经常返回 `EACCES`，
**即使 `fopen` 完全正常**。

**后果**：`frame_dump` 和 `repair` 两个诊断开关长期"文件在、代码在、
永不生效"。为此白跑了好几轮。

**铁律：所有文件开关必须用 `fopen` 探测。**

> 遗留问题：`host_path.c` 的快速路径**仍在用 `access(F_OK)`**
> （2026-11-12 发现）。它只影响性能（误判为不存在会走慢路径），
> 不影响正确性。要改的话改成 `fopen`。

### 4.2 ★★★ 进程内模式禁 `dup2` / `chdir` / `abort()` / 信号处理

app 进程里，进程内模式和 ART 共享一切。这四个会伤运行时：

| 操作 | 后果 |
|---|---|
| `dup2(fd,1/2)` | 换掉整个 app 的 stdout/stderr，冲击 ART → 真机 ANR |
| `chdir` | 影响全局工作目录 |
| `abort()` | 触发核心转储，进程内会拖垮整个 app |
| 接管信号 | 与 ART 自己的 handler 冲突 |

子进程模式（`game/exec` 开关）随便折腾。

### 4.3 ★★ Android 12+ 起不了 app（自动化测试的硬限制）

- `am start` / `cmd activity` → `SecurityException: package=com.android.shell`
- `termux-am` → `Could not connect to socket`（termux-api 未运行）
- `monkey` → `app_process: not found`

**每次都要用户手动点一次 app 图标。**

### 4.4 ★★ Windows 语义和 POSIX 语义的差异要逐个点名

不能假设"应该一样"。每一项都可能变成"文件明明在却读不到"：

- **大小写**：游戏路径是 Windows 上写的（`gfx/ui/ScoreMenu.anm2`），
  文件是小写（`gfx/ui/scoremenu.anm2`）。ext4/F2FS 区分大小写 → ENOENT
- **反斜杠**：`bin\XInput1_3.dll`
- **尾随点**、**保留名**

### 4.5 ★★ 符号链接不会进 APK

Termux 开发环境靠 `packed -> rt/packed -> resources/packed` 这条链蒙过去了，
但 Android 的 `/storage/emulated/0` 是 FUSE，**不支持符号链接**。

真机上 `fopen("packed/afterbirthp.a")` 必然 ENOENT → DLC 一个都打不开
→ 日志回到 19 条 `Failed to open` → `backdrops.xml` 读到旧版
→ `gridgfxroot` 返回 NULL → 崩在 `0x48d604`。

**修法**：在宿主层做前缀回落（`host_path.c`），不依赖文件系统特性。

### 4.6 ★ 同一个 basename 不要在一张表里映射两个路径

**事故**：把根目录 `packed/*.a` 和 `resources/packed/*.a` 都补进表里，
导致游戏**反复 fopen 同一个归档**（实测卡死，日志停在
`packed/repentance_de.a` 无限刷 fopen）。

原因：同一个 basename 出现两次、指向两个不同路径，破坏了 basename → 路径
的映射，表现是无限重试。

**只补 `resources/packed/*.a`。** 那 9 条 `Failed to open packed/*.a`
是**无害的**，不用管。

## 五、诊断方法论（最有价值的一类）

### 5.1 ★★★ 主动调 GL 的探针会崩进程

踩过两次，现场都是 `std::terminate`：
- `glGetProgramiv` / `glGetActiveUniform` 探针 → 崩在 `glDeleteProgram`
- 抓帧路径里加 `glBindFramebuffer` → 同上

**规律**：

| 类别 | 例子 | 风险 |
|---|---|---|
| 只读 guest 内存 | `[pngdec]` `[solid]` `[attrib]` | **低** |
| 只读 `c->eax` / 栈参数 | `[uniform-loc]` `[clear] mask` | **低** |
| **主动调 GL / 改 GL 状态** | `glGetProgramiv` `glBindFramebuffer` | **高** |

**任何主动调 GL 的探针，必须先在本地（子进程模式）跑通，再推真机。**

### 5.2 ★★★ 信号处理器里"看起来没执行"通常是这两个原因

1. **stderr 重定向到文件时是全缓冲** —— 不 `fflush` 就 `_exit`，最后一批
   输出全丢。表现："只打印到 `[SEGV]` 第一行"
2. **处理器里用了 `fopen` / `malloc`** —— 堆可能已被破坏，处理器二次崩溃

**修法**：只用 `write(2)` / `_exit` / `sigaction`。十六进制格式化手写。

**这一条坑了至少三轮。**

### 5.3 ★★★ "守卫恒不报" 先怀疑判据本身写错了

**事故**：写保护 arm 的条件写成 `res_table_contains(块基址)`，
正确是 `res_table_contains(块基址 + 16)`（对象指针 = 块基址 + 块头 16）。
偏移错一位，"表内命中"**恒为 0**，白跑两轮。

**规则**：凡是"守卫恒不报"，先怀疑判据，而不是"真的没问题"。

### 5.4 ★★★ 扫描类诊断必须先用审计，不要先上写保护

**对比**：
- 写保护 + vtable 护栏：五轮，抓到逐字段写，效率低
- 在**外部写入点**埋审计（`res_write_audit`）：**一次命中**

**教训：在外部写入点埋审计，不在受害对象上埋。**

### 5.5 ★★ 探针的计数上限会掩盖数据

- `[uniform-loc]` 上限 20 条，正好被 8×Texture0 + 12×Transform 占满，
  `Texture1` 从未被记录 —— 差点得出错误结论。**改成按名字去重。**
- `[uidraw]` 曾被 8×8 占位白纹理占满名额，一条 UI 数据都没抓到。
- `texdump` 和 `texraw` 共用 `txdumped` 计数器，大纹理把名额挤光，
  32×32 的 HUD 纹理一张都没导出。**多个分支不要共用静态计数器。**

### 5.6 ★★ 用 CPU 侧读数判断纹理好坏会把所有 FBO 附件判成坏图

游戏用**透明画布**（`rep stosd` 铺 `0x00000000`）建离屏 RT，之后用 FBO
往里渲染。CPU 侧采样一块 GPU 渲染目标，读到零是**必然的**。

`[texfinal]` 报的 "14.3% 全零"里混着这批**正常**的离屏画布。

### 5.7 ★★ `fread_covers` 只查最近 512 次 → 索引不可信

加载期有 2400 万次 fread，纹理上传时的记录早已滚出窗口。
**`fread=否` 不可作为证据。**

### 5.8 ★★ 函数入口更新的全局 ID 会过期

`g_last_func_id` 只在函数入口更新，被调用函数返回后仍是旧值。
崩溃时看到"函数ID=309"**不代表**当前真的在 `sub_0000ea90` 里 ——
这次 `ebp=403fe728`（`sub_0048d3f0` 的帧）就是矛盾证据。

### 5.9 ★★ 自己的上一轮结论也要用工具复核

上一轮认定 `[ebp-0x1036c]` 是根因，一个 `STACK_SLOT_WATCH`
（发现它从未被读）就把这个判断推翻了。

### 5.10 ★★ "日志里没有"有两种含义

`grep packed` 为 0 时，先假设"fopen 失败了所以没打日志"，
**实际是"根本没调用 fopen"**。

区分方法：在**上一层的入口**下断，而不是在推测的终点。

### 5.11 ★★ "被调用但没有翻译定义"的桩比空桩更安全

空桩会静默返回 0，产出的是**空结果**而不是报错 —— 调用方按正常路径
继续跑，在很远的地方才崩。

**loud stub**（`guest_fault(c, addr, "untranslated: <指令>")`）
能在日志里直接看到指令名。

### 5.12 ★ `pgrep -f <名字>` 会抓到 shell 自己

按 `/proc/*/comm` 匹配，否则你会对着一个 `do_wait` 的子 shell 采样，
得出"CPU 占用 0"的结论。

## 六、性能：这些坑会让你误判

### 6.1 ★★★ 诊断探针在热路径上会拖垮性能

| 事故 | 代价 |
|---|---|
| 导入分发里加 2 个 `snprintf` × 上亿次 | **多花 9 秒**启动 |
| 每次 fread 加 2 次 `clock_gettime` × 2400 万次 | **1.7 秒** |
| `fontDiag` 一轮 6.8 秒、每 300ms 一次 | 累计 **136 秒**主线程占用，游戏卡到没法玩 |
| 导入逐条日志（IMP_TRACE） | 4000 万行 / **3.3 GB**，写盘把游戏拖慢一个数量级 |

**规则**：
- 热路径只**存指针**，不拷贝（`snprintf` → 直接赋值，600ns → 2ns）
- 诊断默认关，用环境变量或文件开关按需开
- 环形记录（最近 N 条）常开，全量日志默认关

### 6.2 ★★★ `Sleep()` 无条件 `usleep` 把帧率钉在 30fps

**现象**：1017 ms 的帧尖峰 = 1004 ms 睡眠 + 17 ms 实际帧

**原因**：游戏在单线程串行执行 guest 代码，睡眠期间不会有任何进展
（真实 Windows 上那些并行工作线程我们根本没跑）。长睡眠是**纯浪费墙钟时间**。

**修法**：`>16ms` 的请求截到 `1ms`（cap 可配），`<=16ms` 原样保留
（用于帧率节流，截掉会让游戏空转烧 CPU）。

### 6.3 ★★★ 静态指令数 ≠ 性能

`objdump` 数出 -9.1% 指令数，A/B 实跑差异 **0.2%**（噪声内）。

**任何性能结论必须有运行时数据。** 不要用静态指标做优化决策。

### 6.4 ★★ 离屏渲染 ≠ 看不见

pbuffer 恰恰是最好的调试目标：`glReadPixels` 一抓，画面是黑是白、
有没有动，比任何日志都直接。

### 6.5 ★★ 本地测不出真机性能

- 本地帧率被 60fps 封顶
- 本地跑不到字体加载（7800 帧都没有字体图集上传）
- 本地抓帧永远白屏（pbuffer 上 gl4es 的 FBO 链路不正常）
- 本地起不了 app

**帧率、画面、性能的结论必须来自真机。**

### 6.6 ★ 统计"未实现"要区分"正确的故障语义"和真正缺失

除零返回 0、`OpenProcessToken` 返回失败 —— 这些是**正确的行为**，
不是"未实现"。

## 七、缓存与状态：静默失效三连

### 7.1 ★★★ 缓存 key 没变 → 读到旧结果

**事故**：窗口缓存的 key 没包含某个字段，改了那个字段后仍读到旧解码结果，
文本表被劈成两半显示 `"#KEY"`。

### 7.2 ★★ 安全性检查写成"最多 1 次"会拦掉用户所有尝试

**事故**：`options.ini` 改写加了"最多 1 次"计数，把用户所有切换尝试全拦掉，
表现成"三种语言值都没用"，日志只有一句"已尝试改写 1 次"。

**教训：有幂等性测试就不需要全局计数式安全网。**

### 7.3 ★ 替换字符串池只能改短

`ISMG` / `arsc` 都按固定偏移寻址，改长要重排整个池。
**原地替换必须先断言 `新长度 <= 旧长度`。**

## 八、被否决的路线（不要重走）

### 8.1 换 MobileGlues —— 实测否决

1. **shader 转换管线拒绝 Isaac 的 GLSL**（4/4 失败）。Isaac 用 GLSL 1.10
   legacy（`varying` / `attribute` / `gl_FragColor` / `texture2D`，无 `#version`）。
   补 `#version 120` 也失败，原因是 glslang 硬限制：
   `compilation for SPIR-V does not support the compatibility profile`
2. **不支持 client-side vertex array**：后端 context 恒为 GLES 3，
   GLES 3 取消了 client-side array，而 Isaac 零 VBO → 所有几何画不出来
3. 失败还是静默的：转换失败返回原始 GLSL，`ignore_error=Partial` 把
   `COMPILE_STATUS` 改成 `GL_TRUE`

**详细证据见 `EVAL_mobileglues_20261112.md`（如果随包提供）。**

### 8.2 按痛点"重放纹理"补传 —— 实测导致串图

**假设**：游戏在像素写好之前就调了 `glTexImage2D`，所以在 draw 时按原参数
重放一次。

**结果**：`ptr` 是**共用暂存池**，12 个纹理 id 共用同一块地址。重放 =
把最后一张图复制给池上每个 id → **初始房间全是彩色贴图**。

**教训：看到"同一指针先零后非零"不能推出时序错位**，那可能只是两条加载
路径轮流用同一块缓冲。方案代码保留但**默认关闭**（`game/repair` 开关）。

### 8.3 REPENTOGON —— 架构上不可行

LibZHL 扫 x86 字节找 hook 点，而我们的内存里是 **ARM64**。

## 九、工程纪律（血泪总结）

### 9.1 失败路径的日志不能依赖它自己先成功

诊断代码放在失败路径**之后**，就永远看不到失败。第 38 轮 `.so` 化
"点了没反应"就是这个原因。

### 9.2 "失败就回退"必须验证回退路径本身

第 36 轮：只测了主路径，没测回退，结果 libEGL 对无效窗口**段错误**，
回退走不到。

### 9.3 换 wire format 必须同时改 native 和 Java 两端

### 9.4 gl4es 源码注释不等于实现

`h_fopen` 里注释写「Windows 语义：大小写不敏感」，但
`host_path_resolve()` **从来没实现过大小写查找**。

**注释是意图，不是行为。**

### 9.5 大文件只 `grep -n` + `sed -n`，不要整读

gen/ 有 466 万行，整读会撑爆上下文。

### 9.6 测之前 `pkill -9 -x <名字>`

不要后台长跑模拟器（会拖垮 Termux）。

### 9.7 "症状规律"比"病因猜测"更值得先找

这一轮的突破不是来自反汇编，而是把池 dump 下来做**字符串统计**，
发现"以 `/` 结尾的值全都丢"这个规律。

**在通读几千行反汇编之前，先想办法把数据结构打出来做统计。**

### 9.8 确定性是线索

同一个野地址在多次运行中完全相同，说明它不是随机的未初始化垃圾，
而是可复现的计算结果或固定数据 —— 这能直接排除一大类假设。

### 9.9 "排除"和"确认"一样值钱

用三个守卫各拿到 0 条，把 UAF / 双链 / VirtualAlloc 三条路一次性封死，
可能性空间从"无穷"缩到"字形写入"一个方向。

**排查时优先做能证伪的守卫，而不是继续加打印。**

### 9.10 用"写入了哪个地址"反推"执行了哪条指令"，比读反汇编快

轨迹里的 `403fe6c4/6d4/6d8` 直接对上 `[ebp-0x64]/[ebp-0x54]/[ebp-0x50]`，
一步就锁定了一段代码。
